**文档结构**：0 结论速览 → 1 定位与边界（含对外依赖契约表）→ 2 技术栈与运行时 → 3 代码结构与分层 → 4 核心组件（Agent 装配/后端与工作区/工具面/消息适配/状态/中间件/Skill）→ 5 接口清单（HTTP 11 个 + WS 协议）→ 6 主要流程 11 条（启动/建连/单轮/取数/报告交付/压缩/取消/标题/附件/删除/热更新）→ 7 数据模型 → 8 前端 → 9 改造切入点与风险清单 → 10 文件索引 → 附录与既有文档分工。

**关键结论（升级改造相关）**：

1. 架构本质是「框架做执行、自己做状态」：deepagents 0.4.7 只管单次 `astream` 内的中间件链与 ReAct 循环，会话历史与压缩摘要由 `chat_service` 每轮从 MySQL 重建（无 checkpointer / 无 store）。
2. **四个改造主接缝**：A `db_query.py`（取数契约，影响低）· B `_backend_factory`（工作区与后端，影响中）· C `chat_service.run_agent_turn`（单轮编排，影响高）· D `SKILL.md` + `render_report.py`（方法论，可热更）。
3. Agent 单例 + 运行时配置注入（`configurable.workspace_dir`）是「按租户差异化 Agent」的既有接缝；若差异落在构建期（模型/Skill 集），单例模型不成立。
4. WS 鉴权不走 auth introspection：HTTP 换一次性令牌 → WS 用 query 参数 → Redis `GETDEL` 原子消费（TTL 30s）。令牌本身可跨实例，但**工作区在本地磁盘**，是水平扩展的硬约束。
5. 新发现的既有问题（此前文档未列）：`GET /api/chat/ls/{conversation_id}` **未校验会话归属**（其余接口均校验）。已写入风险表。
