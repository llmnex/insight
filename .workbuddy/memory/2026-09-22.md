## insight-agent 联调排障（3 个问题定位）

用户在同一台机器上跑全链路时踩到的坑，均已定位。

### 1. `/api/chat/ws-token` 返回 500 → 前端提示「聊天连接初始化失败」

**根因**：6379 上有**两个 Redis 实例**抢端口。

| 绑定 | PID | 归属 |
|---|---|---|
| `0.0.0.0:6379` + `[::]:6379` | com.docker.backend | Docker 容器 `redis-server`（**无密码**，`CONFIG GET requirepass` 为空） |
| `[::1]:6379` | **wslrelay.exe** | 本机 native redis（**带 requirepass**） |

应用首次连接 Redis 恰好落到 native 那个 → `NOAUTH Authentication required.` →
redis-py 映射成 `redis.exceptions.AuthenticationError: Authentication required.` → 500。

**用户关掉 native redis 后恢复**（实测 `/api/chat/ws-token` 返回 200）。

关键排查手法（可复用）：
- `netstat -ano | findstr ":6379" | findstr LISTENING` 看监听者数量；多于一 = 抢端口
- 用裸 TCP 发 `PING` / `CONFIG GET requirepass` / `INFO server` 取 `run_id` 指纹，判断两个入口是不是同一实例
- 结论：`AuthenticationError: Authentication required.` 是 **Redis 的**，不是 LLM 的 —— 容易被误导

`openai.AuthenticationError: 401 ... 'api key: ****4065 is invalid'`。
同一把 key 也在 `data-agent/conf/.env`，所以要改两处。

### 3. Tavily MCP 正常（`initialize` 返回 200），排除

### 日志排查要点（重要）

- 前端提示高度概括，真实原因只在 `insight-agent/logs/YYYY-MM-DD.jsonl`
- 提示语 → 日志关键字对照：
  - 「聊天连接初始化失败」→ `"path": "/api/chat/ws-token"`
  - 「模型调用失败，请稍后重试。」→ `agent failed` + `AuthenticationError`
- `unhandled_exception_handler` 用 `logger.exception` 但不在 `except` 块内 → **HTTP 500 的日志里没有 traceback**，只有 `exc_type` / `detail`；能拿到堆栈的是 `chat.py` 的 `agent failed`
- `/api/chat/ls`、`/api/chat/create` 不碰 Redis，所以「列表能加载但发消息失败」是 Redis 问题的典型特征

### 4. 日志里出现两条内容相同的 HumanMessage —— 不是 bug

`PatchToolCallsMiddleware.before_agent` 输出 `Overwrite(value=[HumanMessage(id=...207d499d), HumanMessage(id=...049a8391)])`，两条文本一样。
原因：**用户在同一个对话里重发了同一条失败的问题**。

- `_add_message`（`chat_service.py:77`）是**先落库、再调模型** → 一轮失败时用户消息已持久化
- 重发时 `load_conversation_context` 把上一条载入，`_add_message` 再追加一条 → 两条内容相同、`context_seq` 不同
- `PatchToolCallsMiddleware`（`deepagents/middleware/patch_tool_calls.py:44`）只做「给 dangling tool_call 补 ToolMessage」，**原样复制消息、不去重**，所以两条都进了模型输入

**给用户的建议**：失败后新开会话重试，不要在出错会话里反复重发。

`context_seq` 语义（易误判）：空对话 `cur_context_seq = -1`，首条消息 `+=1` → **从 0 开始**递增，不是从 1。

## ⚠️ build_meta_knowledge 不可重复执行（已验证的坑）

`app/repositories/mysql/meta/meta_mysql_repository.py` 的 4 个保存方法**全是 `session.add_all()`** ——
纯 INSERT，**没有 upsert、没有 truncate、没有先清表**。

```python
async def save_table_infos(...):    self.session.add_all(models)
async def save_column_infos(...):   self.session.add_all(models)
async def save_metric_infos(...):   self.session.add_all(models)
async def save_column_metrics(...): self.session.add_all(models)
```

→ **对已构建过的库再跑一次 `build_meta_knowledge`，必然报错**（已复现）：

```
sqlalchemy.exc.IntegrityError
(asyncmy.errors.IntegrityError) (1062, "Duplicate entry
 'dwd_fact_trade_order_detail_di.payable_amount-GMV' for key 'column_metric.PRIMARY'")
[SQL: INSERT INTO column_metric (column_id, metric_id) VALUES (%s, %s)]
```

**正确重建流程**（重跑前必须清表）：
```powershell
cd data-agent
uv run -m app.scripts.init_db                                   # meta.sql 里是 DROP TABLE IF EXISTS，会清空重建
uv run -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml
```

**并发跑两次构建也会撞同样的 PK** —— 只能用单实例构建。

### 各存储的幂等性（决定了重跑的后果）

| 存储 | 写入方式 | 重跑是否安全 |
|---|---|---|
| `meta` MySQL | `session.add_all` 纯 INSERT | ❌ 报 IntegrityError |
| ES `data-agent-value` | 文档 `_id = "{column_id}.{value}"` → 覆盖写 | ✅ 幂等，docs 数不涨 |

## db_query ReadTimeout 的真实原因（不是 data-agent 挂了）

**客户端超时是 300 秒**（`insight-agent/app/core/http_client.py:16`），不是默认 5 秒。

data-agent `/api/query` 耗时画像（`data-agent/logs/conv-7.log` 实测）：
- 正常一次 **80~150 秒**，11 个节点全是 LLM 调用，单节点 15~130 秒
- 偶发卡顿：request `53046606` 在 `filter_table`（11:54:06）**之后 5 分 13 秒零日志** → 累计超 300s → ReadTimeout
- 紧接着 Agent 自己重试的 request `fc006815` **82 秒就跑通了**（11:59:19 → 12:00:41）

**根因是 data-agent 单次调用的 LLM 节点偶发长尾 + 300s 上限偏紧**，不是服务故障。

**缓解手段（按性价比排序）**：
1. **一次 db_query 只问一件事**，别把「月度汇总」+「最大日期」塞进一次调用
2. **单表口径**（用 `order_pay_time IS NOT NULL` 代替 join 支付表）
3. 值写对（`'成功'` 而非 `'支付成功'`），避免 data-agent 花 LLM 轮次纠错
4. 必要时把 `http_client.py` 超时从 300s 调到 600s

## insight-agent Agent 架构分析（新建文档）

产出 `insight-agent/AGENT_ARCHITECTURE.md`：源码直读 + **deepagents 0.4.7 已安装源码交叉验证**（`.venv/Lib/site-packages/deepagents`），覆盖分层架构、单轮 WS 调用 8 步链路、Mermaid 时序图、6 个关键机制、风险分级清单。

**核心事实（与旧记忆 DOC.md 有出入，以下为准）**：

- **LangGraph 无 checkpointer** → 框架不保留跨轮 state（`_summarization_event` 每轮重置）。insight-agent 自己把「摘要 + 摘要后原始消息」在 `load_conversation_context` 里每轮重建 —— 这是压缩设计的真正动因。
- 因此 `_compute_state_cutoff(previous_event=None, cutoff)` 恒等于本轮索引，`seq_offset = cur_context_seq - len(messages) + 1` 是内存下标 ↔ DB `context_seq` 的唯一桥梁
- 压缩阈值 = `profile.max_input_tokens(1,048,576) × 0.85` ≈ **891k tokens**（`summarization.py:161-198`）→ 线上几乎永不触发，压缩链路缺真实流量验证
- 主 Agent 中间件栈顺序：`TodoList → Skills → Filesystem → SubAgent → Summarization → PromptCaching → PatchToolCalls`（`graph.py:270-288`）；`recursion_limit=1000` 硬编码
- 工具面 = 内置 9（含 `execute`/`task`）+ 本地 2（`db_query`/`return_file`）+ MCP；`task` 子 Agent 拿同一套工具（也能查库）
- `return_file` 工具只回元信息，附件由 `message_mapper` 识别 `name=="return_file" && status=="success"` 转成 `Attachment`，前端再走 `/api/chat/attachment/get` 下载

**新发现的风险（未修，建议同步给用户）**：

- **P0**：`execute` 无沙箱 —— `LocalShellBackend` 实现 `SandboxBackendProtocol`，`virtual_mode=True` 只约束文件工具、**不约束 shell**，且 `inherit_env=True` 把宿主环境变量（含 API key）暴露给模型可控命令
- **P1**：外层 `while True` 退出条件依赖 `finish_reason == "stop"`，该值取自 `response_metadata.get("finish_reason")`；provider 不返回时恒为 `None` → **空转重复喂同一 messages**（每次都是完整 LLM + 工具循环）直到被取消
- **P1**：`_execute_agent` 只传 `configurable.workspace_dir`、未传 `thread_id` → 压缩中间件 `_get_thread_id()` 回落随机 `session_{uuid8}` → 历史 offload 文件每次调用都新建，堆在 `workspaces/user_*/*/conversation_history/`
- **P2**：`_add_message` 每条消息一次 `INSERT + commit + refresh`，一轮 N chunk = N 次事务且在流式关键路径上
- **P2**：`_background_title_and_notify` 在 `sleep(3)` 后向**同一个 WebSocket** `send_json`，与消息流并发写同一连接（Starlette 不保证并发安全）
