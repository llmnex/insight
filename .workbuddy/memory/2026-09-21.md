### 关键发现（本项目结构事实）

- 四模块：`insight-agent`（核心，:7300）/ `auth`（:7100，SQLite `data/auth.db`）/ `data-agent`（:8000，NL2SQL）/ `dbmock`（电商数仓数据生成）
- 默认管理员：`admin@123.com` / `123123`（auth 启动时自动创建）
- **前端 `insight-agent/app/static/dist` 已预构建**，FastAPI 直接托管 SPA，跑起来不需要 npm；只有改 `web/` 才需要 `npm run build`
- 基础设施：MySQL 3306 + Qdrant 6333 + ES 9200 由 `data-agent/docker/docker-compose.yaml` 提供（ES 首次需 build 带 IK 插件镜像）；Redis 6379 本机已原生运行
- **端口冲突坑**：`insight-agent/docker/docker-compose.yaml` 也会起 6379 redis，与本机原生 redis 撞端口；且两个 compose 都用 `container_name: mysql-server`，不能同时用
- auth 不校验 client 注册表（代码里只比对 authorize/token 两阶段的 client_id + redirect_uri 一致性），`client_id=insight-agent` 直接可用
- auth 无 session 时重定向到 `{request.base_url}/login`，经 insight-agent 的 `/auth-api` 反代时上游 Host 被替换为 7100，所以登录页正常落在 7100，默认配置无需改 `web_base_url`
- 工作区：`.deepagents/workspaces/user_{uid}/{cid}/`，约定子目录 `raw/`(db_query 落盘) `analysis/` `outputs/`(HTML)
- `db_query` 实际把结果写在**工作区根目录**（`{file_name}.csv`），不是 `db_query_results/`
- **路径坑**：`SKILL.md` 里 `render_report.py` 的示例是 Linux 绝对路径 `/home/kodey/...`；Windows 上应告诉 Agent 用相对工作区路径 `../../../skills/insight/scripts/render_report.py`
- MCP（tavily）与 Skill 加载**串行**，MCP 失败会导致 Agent 起不来 → 排查时先看 `TAVILY_API_KEY`

### 坑：两个项目的建库命令不同名（用户已踩）

| 目录 | 建库命令 |
|---|---|
| `insight-agent` | `uv run app/init_db.py`（**无** `app/scripts/` 目录） |
| `data-agent` | `uv run -m app.scripts.init_db` |

在 insight-agent 里跑后者会报 `ModuleNotFoundError: No module named 'app.scripts'`。
另外 `insight-agent/app/init_db.py` 是 DROP 重建语义，重复执行会清空 `chat` 库历史对话。
已写入 QUICKSTART.md 的 Step 6 提示框 + 排查表。

### 最大坑：两份 docker compose 目录都叫 `docker`，起错了要到很晚才炸

- `insight-agent/docker/docker-compose.yaml` → **只有 MySQL + Redis**
- `data-agent/docker/compose.yml` → **MySQL + Qdrant + Elasticsearch**（无 Redis）
- 两目录 basename 相同 → Compose 项目名同为 `docker`，MySQL/Redis 服务定义逐字相同 → **起错不报错**
- 症状：`build_meta_knowledge` 连 6333/9200 失败；或实际取数时值召回为空
- 判定：`docker ps -a` 看不到 `qdrant` / `elasticsearch`
- 补救（不丢数据，同项目名+同卷 `docker_mysql-data`）：
  `cd data-agent\docker; docker compose up -d qdrant elasticsearch`
- 元数据索引固定命名（无需手建，代码里 ensure_*）：
  ES index `data_agent`；Qdrant collections `data-agent-column` / `data-agent-metric`

### 坑：data-agent 两个脚本的「假报错」与真实前置依赖

- `uv run -m app.scripts.init_db` 输出 4 行 `Unknown table 'meta.table_info'/column_info/metric_info/column_metric`
  → 来自 `meta.sql` 里的 `DROP TABLE IF EXISTS`，MySQL warning 1051，**非报错**，以结尾 `Initialized meta database` 为准。
- `build_meta_knowledge` 的**隐藏硬前置**：它要 `SELECT DISTINCT` warehouse 真实取值写入 ES 做值召回
  （`meta_knowledge_service._save_value_info_to_es` → `DWMySQLRepository.get_column_values`）。
  warehouse 为空时**不报错但索引为空**，导致 NL2SQL 认不出中文枚举（`'退款成功'`、`ALIPAY` 等），取数质量塌陷。
  → 必须先跑完 dbmock 数据生成，再跑 build_meta_knowledge。
- dbmock 的 `core/init_db.py` 只建表结构（warehouse 24 张表），**不生成数据**；数据靠 `uv run -m core.generators.main`。

### 环境注意（Tooling）

- 本机 bash 的 shim 损坏（`dirname: command not found`），`rm`/`ls`/`find` 等外部命令不可用；PowerShell 的 stdout 不回显。
  → **绕行方案**：PowerShell 把结果 `Out-File` 到临时文件，再用 Read 工具读取；优先用 Glob/Grep/Read 原生工具。
